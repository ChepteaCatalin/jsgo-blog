## Feature Flags

React hides breaking changes and unfinished features behind feature flags. This allows the team to experiment with new features without affecting the main build. Before publishing, React's build system strips out disabled feature flags.

React also has an integration job that checks bundle sizes on every commit, helping the team ensure that features are properly gated.

Feature flags are defined in `packages/shared/ReactFeatureFlags.js`. However, some builds require different feature flags. For example, React Native may need different flags than React DOM. These build-specific configurations can be found in `packages/shared/forks`.

## Tests

The React team prefers colocating tests in a `__tests__` directory close to the features they test, rather than keeping them all in a centralized directory. I prefer this approach as well.

## Codebase Overview

React is a monorepo. Its documentation, however, is hosted in a separate repository.

The main top-level directories in the React monorepo include:

- `packages` contains metadata and source code (`src`) for all React packages.
- `fixtures` contains a collection of small React applications that contributors can use to test and experiment with React features.
- `build` contains the build output of React. This directory is generated the first time you build the project.

## Warnings and Invariants

In React, `console.error` is used to log warnings during development. Yes, despite its name, `console.error` is used for warnings. These are the "errors" you typically see in Console in development mode.

```js
if (__DEV__) {
  console.error("Something is wrong.");
}
```

In production builds, these messages are stripped out because the Google Closure Compiler eliminates dead code, including `if (__DEV__)` blocks when `__DEV__` is `false`. This is exactly how React removes development-only warnings from production builds.

Invariants are conditions that must always hold true during program execution. They are essentially assertions. If an invariant is violated, it indicates a serious problem in the code, so React throws an error to signal the issue. Unlike development warnings, invariant violations trigger errors in both development and production modes.

## Development and Production

The `__DEV__` pseudo-variable allows React to differentiate between development and production builds. It is called a pseudo-variable because its value is replaced at build time with a boolean (`true` or `false`). This means you can use it anywhere in the React repository, even though it isn't explicitly defined in the source code.

```js
if (__DEV__) {
  // This code will only run in development.
}
```

During the build process, `if (__DEV__)` is replaced with `if (true)` in development builds and `if (false)` in production builds.

The Google Closure Compiler removes all `if (false)` branches from the minified production build, effectively eliminating development-only code and resulting in a smaller, more efficient production bundle.

The Google Closure Compiler is a Java-based tool distributed through the npm package `google-closure-compiler`. React uses it to minify and optimize production bundles. It performs dead code elimination, minification, and various other optimizations.

Despite the name, it has nothing to do with the ClosureScript programming language.

This also answers my previous question: "Why do I need a Java runtime installed to build React?"

Everything inside an `if (__DEV__)` block is eliminated from the production build by the Google Closure Compiler.

## Flow

Flow, developed by Facebook (now Meta), is a static type checker for JavaScript and is used throughout the React codebase. At first glance, it might look like a less capable version of TypeScript. Files annotated with `@flow` contain Flow type annotations.

## Multiple packages

React is a monorepo. Its repository contains multiple separate packages so that their changes can be coordinated together, and issues live in one place.

## React Core

React "core" includes all the [top-level APIs](https://reactjs.org/docs/react-api.html)

**React core only includes the APIs necessary to define components. It does not include the reconciliation algorithm or any platform-specific code.** It is used both by React DOM and React Native components. **This is an intentional architectural decision that allows the same React core to be used across different environments**. For example, React DOM targets the web, while React Native targets mobile platforms. Each renderer provides the platform-specific rendering logic while sharing the same React core and reconciliation infrastructure.

React Core is located in the `packages/react` directory within the repository. It is published to npm as the `react` package, which exports the `React` identifier.

## Renderers

**A renderer is a piece of software that manages how a React tree turns into the underlying platform calls.**

There are plenty of them:

- `react-dom` renders React components to the DOM.
- `react-native-renderer` is a thin layer that teaches React to interact with React Native, but, React Native itself renders React components to native views (IOS, Android, Desktop etc.).
- `react-test-renderer` renders React components to JSON trees for Snapshot Testing in Jest and maybe other testing tools too.
- `react-art` renders React components to the ART library, which is used for drawing vector graphics in React.

## Reconcilers

Even vastly different renderers like React DOM and React Native need to share a lot of logic. In particular, the [reconciliation](https://legacy.reactjs.org/docs/reconciliation.html) algorithm should be as similar as possible so that declarative rendering, custom components, state, lifecycle methods, and refs work consistently across platforms.

The reconciler is the part of React that implements the reconciliation algorithm. It is shared between React DOM and React Native.

In React 15 and earlier, React used the _Stack Reconciler_. Starting with React 16, it introduced the _Fiber Reconciler_, so it's code is located at `packages/react-reconciler`.

## Event System

React implements a layer over native events to smooth out cross-browser differences. Its source code is located in `packages/react-dom/src/events`.

## Reconciliation algorithm

### Motivation

When a component updates (e.g., when a prop or state changes), its `render()` function is called. This function generates a tree of React elements. On the next render, React generates a new tree. Although the new tree may differ from the previous one, the DOM representation remains unchanged initially. React therefore needs a way to apply the necessary changes to the DOM based on the differences between the two trees.

So, we need to **identify the differences between the previous and the new trees of React elements and apply the minimum set of changes to the DOM to transform the former into the latter**. This process is known as **reconciliation**.

There is a mathematically proven, state-of-the-art algorithm that guarantees finding the **minimum set of changes required to transform one tree into another**, called the **Tree Edit Distance (TED)** algorithm. The problem with this algorithm is that its time complexity is O(n³), where _n_ is the number of nodes in the tree. This makes it impractical for large trees, such as those encountered in real-world React applications. For example, if you have a tree with 1,000 nodes, the algorithm may require on the order of one billion operations, which is clearly not feasible in practice for web applications.

The React team implemented a heuristic algorithm that is not mathematically optimal: it does not guarantee finding the **minimum set of changes required to transform one tree into another**. However, it works efficiently in practice for typical React applications. Its time complexity is O(n), where _n_ is the number of nodes in the tree. This is a significant improvement over the O(n³) time complexity of the Tree Edit Distance (TED) algorithm, achieved by sacrificing optimality for performance.

This algorithm is based on 2 assumptions, which reduces the time complexity from O(n³) to O(n):

1. **Two elements of different types will produce different trees.** If two trees have elements of different types at the same position, React tears down the old tree and builds the new one from scratch. Rather than spending time trying to identify the exact differences between the trees, React assumes that all nodes are different and replaces the old tree entirely to save time.
2. **The developer can hint at which child elements may be stable across different renders with a `key` prop.** Developers can use the `key` prop to hint to React which child elements should be considered stable across different renders.

### The Diffing Algorithm

When diffing two trees, React first compares the two root elements. The behavior is different depending on the types of the root elements.

#### Elements Of Different Types

Whenever the root elements have different types, React will tear down the old tree and build the new tree from scratch.

When tearing down a tree, components are unmounted and old DOM nodes are destroyed. When building up a new tree, new DOM nodes are inserted into the DOM and component instances are mounted. Any state associated with the old tree is lost. That's because of the assumption (1) from above.

In this example, during reconciliation, the existing `Counter` component will be unmounted, and a new `Counter` component will be mounted, causing its state to be reset.

```jsx
<div>
  <Counter />
</div>

<span>
  <Counter />
</span>
```

#### DOM Elements Of The Same Type

When comparing two React DOM elements of the same type, React looks at the attributes of both, keeps the same underlying DOM node, and only updates the changed attributes. For example:

```jsx
<div className="before" title="stuff" />

<div className="after" title="stuff" />
```

By comparing these two elements, React knows to only modify the `className` on the underlying DOM node.

When a component updates, the instance stays the same, so that state is maintained across renders. React updates the props of the underlying component instance to match the new element. No deleting, no unmounting and no state reset occurs.

After handling the DOM node, React then recurses on the children.

#### Recursing On Children

By default, when recursing on the children of a DOM node, React just iterates over both lists of children at the same time and generates a mutation whenever there’s a difference:

```jsx
<ul>
  <li>first</li>
  <li>second</li>
</ul>

<ul>
  <li>first</li>
  <li>second</li>
  <li>third</li>
</ul>
```

React will match the two `<li>first</li>` trees, match the two `<li>second</li>` trees, and then insert the `<li>third</li>` tree.

If you implement it naively, inserting an element at the beginning has worse performance. For example, converting between these two trees works poorly:

```jsx
<ul>
  <li>Duke</li>
  <li>Villanova</li>
</ul>

<ul>
  <li>Connecticut</li>
  <li>Duke</li>
  <li>Villanova</li>
</ul>
```

React will mutate every child instead of realizing it can keep the `<li>Duke</li>` and `<li>Villanova</li>` subtrees intact. This inefficiency can be a problem.

#### Keys

In order to solve this issue, React supports a `key` attribute. When children have keys, React uses the key to match children in the original tree with children in the subsequent tree. For example, adding a key to our inefficient example above can make the tree conversion efficient:

```jsx
<ul>
  <li key="2015">Duke</li>
  <li key="2016">Villanova</li>
</ul>

<ul>
  <li key="2014">Connecticut</li>
  <li key="2015">Duke</li>
  <li key="2016">Villanova</li>
</ul>
```

Now React knows that the element with key '2014' is the new one, and the elements with the keys '2015' and '2016' have just moved. So, this is the explanation of the (2) assumption from above.

Finding a key is usually simple, as most of the cases you have an ID from your backend. When this is not possible, you can hash some part of the element content to generate unique key. **Keys have to be unique between siblings, not globally unique**.

As a last resort, you can pass an item’s index in the array as a key. This can work well if the items are never reordered, but reorders will be slow.

One side note: **rerendering** means calling a component's `render()` function again, while **unmounting** means completely removing the component from the DOM and discarding its state.

#### Downsides

From the 2 heuristic assumptions mentioned above, results 2 downsides:

1. The algorithm will not try to match subtrees of different component types. If you see yourself alternating between two component types with very similar output, you may want to make it the same type. In practice, we haven’t found this to be an issue.
2. Keys should be stable, predictable, and unique. Unstable keys (like those produced by `Math.random()`) will cause many component instances and DOM nodes to be unnecessarily recreated, which can cause performance degradation and lost state in child components.
